Someone asks for a model trained on their documents. Usually what they want is for the model to be able to use those documents, which is a different thing and a much cheaper one. Telling the two apart needs one distinction: what changes the model, and what only changes what the model sees.

## Training

Pre-training produces the parameters. A model is shown enormous quantities of text and repeatedly adjusts its internal numbers to get better at predicting what comes next. The output is a set of weights.

This is the expensive stage, and almost nobody outside a handful of labs does it. It takes specialised hardware running for a long time.

## Fine-tuning

Fine-tuning continues that same process on a smaller, curated set of examples, with a narrower objective. It writes to the parameters, exactly as pre-training does. The difference is scale and intent, not mechanism.

You will see it said that fine-tuning changes behaviour rather than knowledge. Treat that as a rule of thumb rather than a law. Fine-tuning is further training, and further training on a body of material can change what a model produces about that material. The honest version is narrower: fine-tuning is usually a poor and expensive way to get specific, changing facts into a system, and it is often a good way to fix a consistent format, register or task pattern that is awkward to specify in an instruction every time.

There is also a real cost. Training further on a narrow set can make a model worse at things it used to do well.

## Inference

Inference is what happens when you send input and get output. The model reads its parameters and does not write to them. The same weights that answered the last request answer this one.

## Context is not training

Everything you supply at request time, the instruction, the conversation so far, any documents the application pasted in, is input. It shapes the output, sometimes dramatically. It does not change a single parameter.

This is the distinction people most often lose:

| | Changes parameters | Changes what one run sees |
| :--- | :--- | :--- |
| Pre-training | yes | no |
| Fine-tuning | yes | no |
| Prompting | no | yes |
| Retrieval, pasted documents, conversation history | no | yes |

Four different mechanisms get flattened into the single word "learning", and that flattening is where bad architecture decisions start.

## Does it remember?

Not in the file. Nothing you type adjusts the weights of a hosted model as you talk to it.

But applications built around a model can absolutely remember, by storing what you said and putting it back into the input next time. When an assistant recalls your name a week later, some code wrote it down and some code retrieved it. That memory lives in the application, and you can inspect it, edit it and delete it, precisely because it is not in the model.

One caveat so the rule stays accurate rather than absolute. Research systems and some specialised setups do update parameters during operation, and continual-learning methods exist. The point is not that run-time parameter updates are impossible. It is that mainstream hosted models do not do it, so if you are using one, assume the weights are fixed until you have specific evidence otherwise.

## The decision this usually settles

When you want a model to work with information it did not have, ask what kind of information it is.

If the facts are specific, private, or liable to change, put them in the input. Retrieve them and supply them at request time. You can then update them by editing a document rather than by running a training job, and you can show the reader where the answer came from.

If the problem is that the output keeps coming back in the wrong shape or register, and no reasonable instruction fixes it, fine-tuning is worth considering.

Most of the time the request for training is really a request for better context, which is cheaper, faster to change, and easier to inspect when it goes wrong.
