<p><strong>Key takeaways</strong></p>
<ul>
<li>A prompt is an instruction surface, not an operating model.</li>
<li>A system prompt sets standing behaviour for a session; it is configuration, not a request.</li>
<li>A skill is a reusable capability with clearer inputs, outputs, and constraints.</li>
<li>A workflow coordinates several steps, often including multiple skills.</li>
<li>An agent is a runtime actor executing workflows under tools, memory, and policy.</li>
</ul>
</blockquote>
<p>One reason AI systems feel confusing right now is that teams reuse the same words for different layers of the stack. A prompt gets called a workflow. A workflow gets called an agent. A reusable task gets called a prompt template. The result is architectural ambiguity.</p>
<p>That ambiguity matters because each layer solves a different problem. If the team cannot name the layer correctly, it usually cannot govern or improve it correctly either.</p>
<h3 id="what-is-the-simplest-way-to-separate-these-terms">What is the simplest way to separate these terms?</h3>
<p>A prompt is a one-step instruction. A skill is a reusable capability. A workflow is a sequence of steps. An agent is the runtime actor that executes or coordinates those steps. The layers relate to one another, but they are not interchangeable.</p>
<p>In practice, <span class="highlight">clarity in naming prevents architecture drift later</span>.</p>
<aside class="callout callout-insight">
  <p><strong>Design note.</strong> If you cannot point to where the prompt ends and the runtime begins, the system is usually harder to debug, evaluate, and scale.</p>
</aside>

<h2 id="act-i-why-the-confusion-persists">Act I: Why the confusion persists</h2>
<h3 id="same-language-different-layers">Same language, different layers</h3>
<p>The confusion is understandable because all these things involve natural language:</p>
<ul>
<li>you write prompts in language</li>
<li>you define skills in language</li>
<li>workflows are often described in language</li>
<li>agents may appear to &quot;reason&quot; in language</li>
</ul>
<p>But shared medium does not mean shared role.</p>
<p>A prompt is closest to the request surface. It initiates a task. A skill packages a task so it can be reused. A workflow sequences tasks toward an outcome. An agent executes or coordinates tasks within a runtime that includes tools, state, and policy.</p>
<h3 id="why-this-confusion-is-costly">Why this confusion is costly</h3>
<p>When these are mixed up, teams make weak design choices:</p>
<ul>
<li>they try to improve workflows only by editing prompts</li>
<li>they call a reusable task a skill without defining output boundaries</li>
<li>they describe an agent as if it were just a chat surface</li>
<li>they skip governance because the architecture is still spoken about too vaguely</li>
</ul>
<p>This is why a comparison page matters. The vocabulary shapes the system.</p>

<h3 id="where-does-a-system-prompt-fit">Where does a system prompt fit?</h3>
<p>A system prompt is still a prompt, but it operates at a different range. An ordinary prompt shapes one interaction. A system prompt shapes every interaction inside a session or product surface, and it stays in the context window whether or not the current task needs it.</p>
<p>That makes it closer to configuration than to a request. It is a good place for tone, role boundaries, refusal rules, and output conventions. It is a poor place for task logic, because task logic written into a system prompt applies even when it is irrelevant, and it competes for context with the work itself.</p>
<p>The practical line is about range, not importance:</p>
<ul>
<li>if the instruction should apply to everything in this session, it belongs in the system prompt</li>
<li>if it applies to one repeated task, it belongs in a skill</li>
</ul>
<p>A system prompt that keeps accumulating task-specific rules is usually a skill that has not been named yet. That is the most common version of this mistake, and it is expensive because the rules become invisible. Nobody reviews a system prompt the way they review a capability.</p>
<h3 id="where-workflows-fit">Where workflows fit</h3>
<p>Workflows are the bridge between skills and agents.</p>
<figure class="diagram">
  <iframe src="/scenes/skills-staircase.html" title="Prompt to skill to workflow to agent stack" loading="lazy" scrolling="no" style="pointer-events: none;"></iframe>
  <figcaption>Workflows coordinate reusable skills, and agents execute those workflows inside a governed runtime.</figcaption>
</figure>
<p>A workflow might include several skills:</p>
<ul>
<li>classify incoming task</li>
<li>retrieve relevant context</li>
<li>draft a structured plan</li>
<li>validate output shape</li>
<li>escalate if risk threshold is crossed</li>
</ul>
<p>That workflow may be executed by an agent system, but the workflow itself is not the same thing as the agent. The agent is the runtime actor; the workflow is the structure it follows.</p>
<p>If you want the practical asset layer behind this distinction, see <a href="/shelf/shared-resources/ai-skill-design-templates/">AI skill design templates</a>.</p>
<h2 id="act-iii-applying-the-distinction">Act III: Applying the distinction</h2>
<h3 id="a-practical-decision-rule">A practical decision rule</h3>
<p>When a team asks, &quot;What should we build here?&quot; the following rule helps:</p>
<ul>
<li>if it is a one-off request, use a prompt</li>
<li>if it is a repeated bounded task, define a skill</li>
<li>if it joins several steps together, define a workflow</li>
<li>if it needs tools, memory, and policy in live execution, design the agent runtime</li>
</ul>
<p>That rule is simple, but it removes a lot of conceptual waste.</p>
<p>It also aligns with <a href="/docs/natural-language-programming-stack/">Dual NLP for AI-assisted SDLC</a>. That page is strongest when read as the bridge from intent to structured capability. In that framing, the sandbox is not just a place to play with wording. It is the place where a vague request can be compiled into a more explicit skill blueprint.</p>
<h3 id="common-misclassifications">Common misclassifications</h3>
<p>Several mistakes appear repeatedly:</p>
<ul>
<li>calling a prompt template a skill even though nothing about reuse is defined</li>
<li>calling a workflow an agent because it uses several tool calls</li>
<li>calling an agent &quot;smart&quot; when the real improvement came from better workflow structure</li>
<li>calling a reusable task architecture &quot;prompt engineering&quot;</li>
</ul>
<p>These mistakes slow improvement because they focus attention on the wrong layer.</p>
<p>For prompt-specific context, see <a href="/systems/prompting-is-not-the-skill-you-think-it-is/">Prompting Is Not the Skill You Think It Is</a>. For runtime execution context, see <a href="/systems/agent-instructions-and-handoff-as-an-operating-system/">Agent Instructions and Handoff as an Operating System</a>.</p>
<h3 id="what-this-changes-in-practice">What this changes in practice</h3>
<p>You design the right thing at the right level: prompts for one-offs, skills for reusable tasks, workflows for coordination, and agents for governed runtime execution.</p>
