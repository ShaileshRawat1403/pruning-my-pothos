14:T1daf,<p>AI systems get drawn as boxes with arrows. Somebody adds a box for retrieval, one for the model, one for tools, one for logging, and the diagram looks complete.</p>
<p>The boxes are the easy part. Which ones a given application needs depends on the job it does, and plenty of useful systems have three of them. What the diagram never shows is the thing that actually decides how the system behaves: what each arrow is carrying, and what the box at the other end believes it received.</p>
<h2 id="what-this-page-is-for">What this page is for</h2>
<p><strong>The detailed pages explain individual mechanisms. This one is about where responsibility transfers between them, and which part to inspect when something goes wrong.</strong></p>
<p>That is a different question from what the parts are, and it is not answerable from inside any one of them. Each component can be designed well, tested on its own terms, and correct by its own definition, while the system built from them produces a wrong answer that nobody&#39;s component is responsible for.</p>
<h2 id="what-the-model-contributes">What the model contributes</h2>
<p><strong>The model generates candidate outputs. The surrounding system supplies context, validates contracts, controls effects, preserves state, and records and evaluates behaviour.</strong></p>
<p>Not every application does all of those. A system that summarises a document and shows the result to a person supplies context and does little else, and that is a complete architecture for that job.</p>
<p>What is worth being exact about is the model&#39;s specific contribution. It produces a candidate. Generation does not establish that the candidate is true, does not authorize anything, and does not establish that the task was accomplished. Those are three separate things that three other mechanisms may or may not be doing, and the habit of saying the model <em>decides</em> or <em>knows</em> quietly assigns them to it.</p>
<p>The rest of the system is not a wrapper around that capability. It is where those other questions get answered, when the job requires answering them.</p>
<h2 id="the-assumption-that-crosses-each-boundary">The assumption that crosses each boundary</h2>
<p>Here is the principle the rest of this page is an application of.</p>
<p><strong>A downstream component should not assume a stronger guarantee than the upstream component actually provides.</strong></p>
<p>It sounds obvious stated baldly. It is easy to violate, because the violation is invisible: the upstream component returns something with a name, and the name suggests more than the thing establishes.</p>
<p><em>Retrieved</em> suggests relevant and current. It establishes that a selection process returned something. <em>Validated</em> suggests correct. It usually establishes that a shape matched. <em>Authorized</em> suggests appropriate. It establishes that a rule permitted it. <em>Stored</em> suggests available and true. It establishes that a write succeeded.</p>
<p>Each of those is a real guarantee and worth having. None of them is the stronger guarantee its name implies.</p>

<h2 id="a-request-traced">A request, traced</h2>
<p>Here is an illustrative walk through one request. It is a constructed example, not a description of a particular system, and a real application may skip several of these steps or repeat others.</p>
<p>A user asks for something. The application selects material it judges relevant and supplies it with the request. The model returns a candidate. If downstream software needs a particular shape, a check confirms the shape. If the candidate proposes an action with a real effect, a separate decision determines whether that action may proceed. If it proceeds, something needs to confirm the effect rather than the response. State is updated where the work continues later. Signals are preserved where the behaviour may need investigating. The result reaches a person or another system.</p>
<p>Now watch one assumption cross wrongly.</p>
<p>The selection step returns a document that is six months out of date. Nothing in the pipeline is broken by that. The model conditions on it and still produces a fluent, specific, well-formed answer. The schema check passes, because the shape is right. The policy check passes, because the operation is permitted. The tool call succeeds, because the API accepted it. The state update succeeds. The trace is complete and accurate.</p>
<p>And the effect is wrong, because the subsequent schema, policy and tool checks in this example were not designed to test whether the supplied context was current. A stale premise can survive several locally successful checks when those checks are testing different properties.</p>
<h2 id="local-success-is-not-system-success">Local success is not system success</h2>
<p>That example is the general case, and it is the strongest reason this page exists.</p>
<p><strong>Each part can satisfy its own narrow contract while the workflow as a whole produces the wrong result.</strong> Retrieval returned documents. The model returned parseable output. The schema matched. The API returned success. The state was written. The log entry exists. Every one of those is a true local fact, and none of them is the outcome anyone wanted.</p>

<p>This is also why the end-to-end behaviour needs <a href="/systems/evaluation-is-a-human-problem/">judging on its own terms</a> rather than inferred from component health. A dashboard of green components is a claim about components.</p>
<p>There is a second cost, and it is organisational rather than technical. Where responsibility at a boundary is unclear, each component can be improved against its own measures without anything addressing the boundary itself. Local component metrics can improve while end-to-end behaviour stays the same, if no check covers the boundary assumption that is failing.</p>
<h2 id="which-seam-to-inspect">Which seam to inspect</h2>
<p>The useful version of that observation is diagnostic rather than statistical. A seam is worth inspecting when one part is assuming something the previous part never established.</p>
<p>That converts a vague question into a short list. Was the material actually current, or only retrieved? Did anything check meaning, or only <a href="/systems/structured-output-and-why-it-matters/">shape</a>? Did anything confirm the <a href="/systems/from-agent-intent-to-governed-execution/">effect</a>, or only the response? Was the state still true when it was read, or only present? Where a person was involved, were they <a href="/systems/human-in-the-loop-is-a-system-design-choice/">positioned to judge</a>, or only asked to approve?</p>
<p>Each of those points at a specific mechanism with a page of its own. What this page adds is knowing which one to open.</p>
<h2 id="where-these-responsibilities-actually-live">Where these responsibilities actually live</h2>
<p>A boundary in a diagram is not a boundary in the software.</p>
<p>Several of these responsibilities can live in one function. Selecting context, calling the model and checking the result can be forty lines in one file, and that file is a perfectly reasonable architecture for a small system. The responsibilities are still distinct, and the questions above still apply to it.</p>
<p>The reverse happens too. One responsibility can be spread across a library, a service and a manual step. When a conceptual responsibility spans several implementation surfaces like that, ownership of it may need to be assigned explicitly rather than inferred from where the code sits.</p>
<p>So the diagram describes what the system is responsible for, not how it is deployed. A conceptual box does not imply a separately deployed service, and a single code path may still contain several of these boundaries.</p>
<p>What crosses each boundary varies as much as where it lives: a function argument, a structured object, a row in a database, a queue message, text in a prompt, a person deciding. Making the dependency explicit does not require making it a formal contract. An ordinary function call with a well-chosen name can carry a boundary perfectly well, provided what it carries is understood.</p>
<h2 id="it-is-not-a-pipeline">It is not a pipeline</h2>
<p>The walk above reads as a sequence, which is a property of prose rather than of systems.</p>
<p>Real applications retrieve more than once and sometimes not at all, call no tools, branch on what came back, retry, stop and ask a person, do deterministic work between model calls, or finish at generation with nothing further. A fixed order is one possible shape rather than the definition of the architecture, and any ordering presented as the default is answering a question about someone else&#39;s system.</p>
<h2 id="replacing-the-model">Replacing the model</h2>
<p>Explicit boundaries make a component easier to change. It is worth being careful about how much easier.</p>
<p>Models differ in context size, in how they take tool definitions, in output tendencies, in latency, in modality support, in provider interface and in refusal behaviour. A clean boundary reduces coupling to any of these, and it does not make the model a drop-in part. The work after a swap is usually smaller and rarely zero, and calling it interchangeable sets an expectation the next migration will correct.</p>
<h2 id="what-this-changes">What this changes</h2>
<p>When the next architecture diagram arrives, the components are the part everyone will discuss. Ask about the arrows instead.</p>
<p>For each one: what did the thing on the left actually establish, and what is the thing on the right treating as settled? Where those two differ, you have found either a gap worth closing or a check somebody already wrote. Both are worth knowing about, and neither is visible from the boxes.</p>
