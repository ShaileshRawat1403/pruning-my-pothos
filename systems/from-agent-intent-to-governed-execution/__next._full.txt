39:T4cf,<p>A model asks to issue a refund. Somewhere between that request and money moving, a series of decisions happens. In many systems those decisions are implicit, which means they are being made by whichever code happens to run first.</p>
<p>This page is about making them explicit, because each one fails in a different way and needs a different fix.</p>
<h2 id="the-path">The path</h2>
<p><strong>A model can produce a request for an action. Software outside the model determines whether that request is allowed to become an effect.</strong></p>
<p>Between the two, four things happen:</p>
<p><strong>Check the request.</strong> Is it well-formed? Does it name a real operation, with arguments of the right types referring to things that exist? This is the <a href="/systems/structured-output-and-why-it-matters/">structured output</a> work, applied at the moment before action.</p>
<p><strong>Decide whether it is permitted.</strong> Separately from whether it parses, should this run, for this user, in this context, right now?</p>
<p><strong>Run it.</strong> Call the tool, with whatever limits apply.</p>
<p><strong>Check what happened.</strong> Not whether the call returned, but whether the thing you wanted is now true.</p>

<p>That is a sequence, not an architecture. Small systems collapse it into a few lines of code, and it still helps to know which of the four a given line is doing.</p>
<h2 id="permission-is-its-own-question">Permission is its own question</h2>
<p><strong>Authorization asks whether an operation is permitted, which is a different question from whether the request is well-formed.</strong></p>
<p>This gets confused with four other things routinely:</p>
<ul>
<li><strong>Authentication</strong> establishes who is asking. Permission is about what they may do.</li>
<li><strong>Schema validation</strong> establishes the request is well-shaped. A perfectly formed request to delete a production table is perfectly formed.</li>
<li><strong>Model confidence</strong> is a property of generation. It is not a permission signal and should not be used as one.</li>
<li><strong>Human approval</strong> is one way to resolve a permission question, not the same thing as having one.</li>
</ul>
<p>In practice this layer answers questions with concrete answers: is this tool available to this caller, is this resource inside the scope they were granted, does the amount exceed a threshold that requires something extra. Keep those rules in code you can read, separate from the instruction text, because a rule inside a prompt is a request and a rule in the authorization layer is a check.</p>
<h2 id="when-the-answer-is-not-obvious">When the answer is not obvious</h2>
<p>Sometimes the system cannot tell whether an action should proceed. Treating that as a binary produces bad outcomes at both ends: block everything useful, or let everything through.</p>
<p>Four responses are usually enough:</p>
<table>
<thead>
<tr>
<th align="left">Mode</th>
<th align="left">When</th>
<th align="left">What it leaves behind</th>
</tr>
</thead>

<td align="left"><strong>allow</strong></td>

<td align="left">The action and its verification</td>
</tr>
<tr>
<td align="left"><strong>ask</strong></td>

<p>Choosing between them comes down to three things: whether policy permits it at all, whether there is enough evidence to justify it now, and how expensive the mistake is to undo. That last one does most of the work. An action that can be reversed in a click deserves a different threshold from one that emails a customer.</p>
<p>It also helps to know what kind of uncertainty you have. Missing or conflicting inputs usually call for getting more context. Several plausible options with nothing to separate them calls for a tighter constraint or a second check. An action that will technically succeed while possibly being the wrong thing to do calls for reversibility or a person. These need different responses, so collapsing them into &quot;the system was unsure&quot; loses the information you need.</p>
<p>When the answer is that a person should decide, this page hands over. Who reviews it, what they see, and whether they are positioned to say no is <a href="/systems/human-in-the-loop-is-a-system-design-choice/">human judgment</a>, and it is a real design problem rather than a checkbox.</p>
<h2 id="the-tool-returned-success">The tool returned success</h2>
<p><strong>A successful tool call is not proof that the intended effect occurred.</strong></p>
<p>An API can return 200 while the record it was supposed to update is unchanged, or updated in a way that gets rejected downstream a moment later. A file write can succeed to the wrong path. A message can send to an address that bounces.</p>
<p>So verification is a separate step. A successful response establishes what the interface reports about the call. Where the thing you wanted is a change of state, check that state rather than treating the response as proof of it. Read the record. Confirm the balance.</p>
<p>This is the difference between a step that reports done and a step that shows done. Completion should be evidenced rather than stated, and the gap between those two is where a surprising number of confident, wrong systems live.</p>
<h2 id="classifying-what-went-wrong">Classifying what went wrong</h2>
<p>Once the path is explicit, failures stop being one undifferentiated category. They fall out as:</p>
<ul>
<li>policy denied it</li>
<li>the tool errored</li>
<li>verification failed</li>
<li>required evidence was missing</li>
<li>it exceeded a time or cost limit</li>
</ul>
<p>Each leads somewhere different. A denial might mean the policy is too broad or correctly protective. A verification failure means the tool lied to you, or you checked the wrong thing. Without those classes, incident review turns into narrative: debugging becomes storytelling instead of engineering, and the same fix gets applied to unrelated problems.</p>
<p>Keeping a record of each decision is what makes this possible, and what belongs in that record over time is <a href="/systems/observability-first-ai-systems/">observability</a>. This page only claims the narrower thing: you cannot classify a failure at a boundary you never made explicit.</p>
<h2 id="what-stays-probabilistic">What stays probabilistic</h2>
<p>None of this makes the system deterministic. The model still varies, and a policy check does not change that.</p>
<p>What the checks give you is a dependable answer about one candidate action: given these rules and this request, permitted or not, every time. The variation stays upstream where it belongs, and the decisions about effects stop inheriting it.</p>
