<h2 id="act-i-the-ceiling-on-text">Act I: The ceiling on text</h2>
<h3 id="why-can-a-text-reply-not-carry-a-workflow">Why can a text reply not carry a workflow?</h3>
<p>An assistant can answer a question well. Moving someone from that question to a finished outcome, a booked appointment, a resolved dispute, a completed purchase, asks for more than text. It needs interface pieces that show options side by side, structured comparisons the user can act on, and safe actions wired to real systems.</p>
<p>Prose is sequential. A workflow is not. The moment a user needs to compare three options, see a live number update as they adjust a variable, or trust that clicking a button will not silently do the wrong thing, text alone runs out of road.</p>
<p>In practice, <span class="highlight">the entry point is moving into the assistant, and a plain reply does not travel with it</span>.</p>
<aside class="callout callout-insight">
  <p><strong>Design note.</strong> The practical question is not whether to add a chatbot. It is where the experience should live, and how much of a workflow it can actually complete once it is there.</p>
</aside>
<h3 id="two-production-patterns">Two production patterns</h3>
<p>Most teams building for assistants land on one of two shapes.</p>
<div class="table-scroll-wrap">
  

<table class="comparison-table">
    <thead>
      <tr>
        <th>Pattern</th>
        <th>What it delivers</th>
        <th>Where it breaks down</th>
      </tr>
    </thead>
    <tbody>
      <tr>
        <td><strong>Reply-only chatbot</strong></td>
        <td>Fast to ship, answers questions, links out to a website for anything transactional</td>
        <td>Loses the user at the exact moment they were ready to act</td>
      </tr>
      <tr>
        <td><strong>In-chat app</strong></td>
        <td>Renders structured state and completes the action inside the conversation</td>
        <td>Needs a shared widget system, or every task becomes a one-off build</td>
      </tr>
    </tbody>
  </table>


</div>
<p>The second pattern only stays affordable if the interface pieces are reusable across tasks. That reuse is the actual engineering problem.</p>
<h2 id="act-ii-the-widget-layer">Act II: The widget layer</h2>
<h3 id="what-an-in-chat-app-actually-needs">What an in-chat app actually needs</h3>
<p>Underneath a chat-native app is a small library of interface pieces, composed differently per task rather than rebuilt from zero each time:</p>
<ul>
<li>cards for discovery and comparison</li>
<li>charts, gauges, and structured summaries for decision support</li>
<li>maps for anything location-bound</li>
<li>selectors, steppers, and calculators for input</li>
<li>action components, checkout, booking, confirmation, that close the loop</li>
</ul>
<p>A commerce flow, a booking flow, and a support flow look different on the surface, but they draw from the same pieces underneath. Once that shared layer exists, adding a new task is closer to composition than to a fresh build.</p>
<h3 id="choosing-a-surface">Choosing a surface</h3>
<p>The same capability layer can usually be delivered through more than one surface, and the right choice depends on the job rather than on preference. Tool-connected surfaces suit governed workflows where the assistant needs deep access to documents and structured actions. Native discovery surfaces suit customer-facing journeys where reach and low-friction access matter more than depth of tool access. Picking the wrong one does not fail loudly; it just quietly limits what the app can safely do.</p>
<p>This is a design and governance decision, not a technical afterthought. See <a href="/systems/ai-agents-vs-ai-workflows/">AI agents vs AI workflows</a> for how that same choice plays out one layer down, at the orchestration level rather than the surface level.</p>
<h2 id="act-iii-demo-to-production">Act III: Demo to production</h2>
<h3 id="a-worked-example">A worked example</h3>
<p>A concrete illustration of this pattern: Newtuple published a <a href="https://www.newtuple.com/post/native-ai-apps-inside-chatgpt-and-claude">proof of concept</a> spanning commerce, healthcare, finance, and real estate scenarios, each rendered as a live in-chat app inside two different assistants from one shared widget system. It is a useful reference point precisely because it shows the reuse claim above holding up across four genuinely different workflows rather than one narrow demo.</p>
<h3 id="what-a-production-build-adds">What a production build adds</h3>
<p>A proof of concept proves the experience layer. It usually runs on mock data, with no live backend behind it. Getting from there to something real adds a predictable set of layers:</p>
<ol>
<li>Live integration to real catalogs, records, and transaction systems in place of mock data.</li>
<li>Authentication and permissions, so actions run against the right account with the right scope.</li>
<li>Evaluation, so quality and safety are checked before and after release, not assumed.</li>
<li>Monitoring and human approval for the steps that change real state.</li>
</ol>
<p>None of that is exotic. It is the same governance layer any production AI system needs, applied to a surface that happens to render inside a chat window instead of a page. For the runtime version of that governance layer, see <a href="/systems/engineering-agentic-systems-for-reliability/">Engineering Agentic Systems for Reliability</a> and <a href="/systems/structured-output-and-why-it-matters/">Structured Output and Why It Matters</a>.</p>
<h3 id="what-this-changes-in-practice">What this changes in practice</h3>
<p>Stop treating the assistant as a place to add a chatbot. Treat it as a surface your application can render on, with the same interface discipline and the same production controls you would demand anywhere else. The conversation is the entry point; the workflow still has to be engineered.</p>
