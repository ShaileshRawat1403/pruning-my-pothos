<p><strong>Key takeaways</strong></p>
<ul>
<li>A prompt gives an instruction; a skill packages a reusable capability.</li>
<li>Skills are useful because they preserve constraints, inputs, and expected outputs across runs.</li>
<li>Workflows orchestrate skills, and agent systems execute those workflows in runtime.</li>
<li>If a repeated task cannot be described, tested, and reused, it is not yet operating like a skill.</li>
</ul>
</blockquote>
<p>This guide helps teams and builders design robust capabilities. The term &quot;skill&quot; is getting popular because teams have started to notice the same architectural problem in many tools. A model can respond well once, but that does not automatically create a reliable capability you can reuse inside a larger system.</p>
<p>That gap matters. If every repeated task has to be re-explained from scratch, the system remains conversational instead of operational. A skill is the first step toward making repeated language work behave more like software.</p>
<h3 id="what-is-a-skill-in-practical-terms">What is a skill in practical terms?</h3>
<p>A skill is a reusable execution unit built around a repeated task. It defines what the task is for, what inputs it expects, what constraints shape it, and what output contract it should satisfy. In AI systems, a skill sits between a raw prompt and a larger workflow.</p>
<p>In practice, <span class="highlight">a skill is useful when it reduces interpretation debt across repeated runs</span>.</p>
<aside class="callout callout-insight">
  <p><strong>Design note.</strong> A skill should feel small enough to reuse and explicit enough to evaluate. If it is too vague, it collapses back into a one-off prompt. If it is too large, it behaves like an entire workflow.</p>
</aside>

<h2 id="act-i-where-skills-fit">Act I: Where skills fit</h2>
<h3 id="from-instruction-to-capability">From instruction to capability</h3>
<p>Many teams begin with direct prompting:</p>
<ul>
<li>ask the model to summarize</li>
<li>ask it to draft a spec</li>
<li>ask it to propose a refactor</li>
<li>ask it to write tests</li>
</ul>
<p>This is fine for exploration. It becomes weak when the same task appears over and over and still depends on informal phrasing each time.</p>
<p>That is the point where a repeated instruction should become a named capability. The useful sequence looks like this:</p>
<ol>
<li><strong>Intent</strong>: what outcome is needed?</li>
<li><strong>Prompt</strong>: what instruction initiates the task?</li>
<li><strong>Skill</strong>: how is that task packaged for reuse?</li>
<li><strong>Workflow</strong>: how does the skill connect to adjacent tasks?</li>
<li><strong>Agent system</strong>: what runtime executes and governs the workflow?</li>
</ol>

  <figcaption>A skill is the reusable unit between a one-time prompt and a larger orchestrated workflow.</figcaption>

<h3 id="why-skills-appear-now">Why skills appear now</h3>
<p>Different platforms use different names:</p>
<ul>
<li>skills</li>
<li>tools</li>
<li>actions</li>
<li>tasks</li>
<li>extensions</li>
</ul>
<p>The naming changes, but the architectural need is the same. Systems need reusable units of execution that can be invoked repeatedly without rewriting the entire context every time.</p>
<p>This is why skills matter in AI-assisted SDLC. Repeated tasks like &quot;summarize diff risk,&quot; &quot;compile release notes,&quot; or &quot;generate a constrained implementation plan&quot; should not stay as ad hoc instructions forever. They should become stable operating units.</p>

<p>This is also why skills fit naturally with <a href="/systems/agent-instructions-and-handoff-as-an-operating-system/">Agent Instructions and Handoff as an Operating System</a>. Once a skill is named and bounded, it can be governed more cleanly inside a larger agent workflow.</p>
<h3 id="what-belongs-inside-a-skill">What belongs inside a skill</h3>
<p>A useful skill usually contains:</p>
<ul>
<li>one objective</li>
<li>known input expectations</li>
<li>clear constraints</li>
<li>an output contract</li>
<li>some way to judge success or escalation</li>
</ul>
<p>It does not need to be a full platform feature. It needs to be reusable enough that another run, another person, or another agent can invoke it with roughly the same intended behavior.</p>
<p>If you want the comparative model, continue to <a href="/systems/skills-vs-prompts-vs-agents/">Skills vs Prompts vs Agents</a>. If you want templates to define these more concretely, see <a href="/shelf/shared-resources/ai-skill-design-templates/">AI skill design templates</a>.</p>
<p>The same idea also fits the <a href="/docs/natural-language-programming-stack/">Dual NLP for AI-assisted SDLC</a> page. In that model, natural language first interprets intent, then NLPg compiles that intent into a more governed execution form. A skill sits exactly at that transition point.</p>
<h2 id="act-iii-using-skills-well">Act III: Using skills well</h2>
<h3 id="when-a-task-should-become-a-skill">When a task should become a skill</h3>
<p>A task usually deserves skill status when:</p>
<ul>
<li>it happens often enough to justify reuse</li>
<li>it has recurring inputs and expected outputs</li>
<li>quality depends on a stable constraint set</li>
<li>the team wants to evaluate or version it over time</li>
</ul>
<p>That means not every prompt should become a skill. Exploratory work can remain conversational. Repeated work should become more structured.</p>
<p>If you want to see the handoff point in a concrete local-tool workflow, use <a href="/shelf/local-experiments/ollama-launch-integrations/">Ollama launch: integration handoff</a>. It shows what happens when a reusable capability stops being just an idea and starts behaving like a named operating surface.</p>
<h3 id="failure-patterns">Failure patterns</h3>
<p>Teams usually misuse skills in three ways:</p>
<ul>
<li>calling any prompt a skill</li>
<li>making skills so broad they become full workflows</li>
<li>ignoring output contracts and then claiming the skill is reusable</li>
</ul>
<p>These failures are predictable because they come from unclear boundaries.</p>
<p>For the conceptual comparison layer, see <a href="/systems/skills-vs-prompts-vs-agents/">Skills vs Prompts vs Agents</a>. For runtime framing, see <a href="/systems/tech-stack-for-nlpg-driven-ai-assisted-sdlc/">Tech Stack for NLPg-Driven AI-Assisted SDLC</a>.</p>
<h3 id="what-this-changes-in-practice">What this changes in practice</h3>
<p>You stop treating repeated language work as informal conversation and start treating it as a reusable capability that can be named, tested, and orchestrated.</p>
