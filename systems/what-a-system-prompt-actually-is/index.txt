<p><strong>Key takeaways</strong></p>
<ul>
<li>A system prompt is configuration, not a request.</li>
<li>It is resident: present on every turn, paid for on every turn.</li>
<li>It is the right home for tone, role and output conventions.</li>
<li>It is the wrong home for task logic, because task logic written there becomes invisible to review.</li>
</ul>
</blockquote>
<p>Most teams write their first system prompt in about four minutes and then never look at it again. It gets a role sentence, a tone instruction, maybe a rule about not inventing facts. It works. So it stays.</p>
<p>Six months later it is nine hundred words, four people have added to it, nobody has removed anything, and the last person to read it end to end was the person who wrote the first version.</p>
<p>That is not a discipline problem. It is a structural one, and it comes from treating a configuration file as if it were a conversation.</p>
<p>This article is for practitioners and engineering teams configuring agent runtimes who need to separate global session boundaries from modular execution capabilities. Understanding where configuration ends and execution begins requires untangling <a href="/systems/skills-vs-prompts-vs-agents/">Skills vs Prompts vs Agents</a> and recognizing <a href="/systems/what-a-skill-is-in-ai-systems/">What a Skill Is in AI Systems</a>. Practical verification templates can also be inspected in our <a href="/shelf/shared-resources/">Shared Resources</a>.</p>

<h2 id="act-i-why-the-system-prompt-grows">Act I: Why the system prompt grows</h2>
<h3 id="what-is-a-system-prompt">What is a system prompt?</h3>
<p>A system prompt is a set of instructions loaded before a session begins and held in context for its entire duration. It is not addressed to a task. It describes the conditions under which every task will be handled.</p>
<p>An ordinary prompt asks for something. A system prompt establishes what is true before anything is asked.</p>
<p>That difference sounds small in a sentence and turns out to be the whole thing in practice, because it determines three properties: the system prompt applies whether or not it is relevant, it costs context on every turn, and <span class="highlight">it is read by the model far more often than it is read by a person</span>.</p>
<aside class="callout callout-insight">
  <p><strong>Design note.</strong> The question is never whether a rule is good. It is whether the rule should be true on every turn of every session. That single test sorts almost everything.</p>
</aside>
<h2 id="act-ii-where-the-line-actually-sits">Act II: Where the line actually sits</h2>
<h3 id="how-is-a-system-prompt-different-from-a-skill">How is a system prompt different from a skill?</h3>
<p>The honest answer is range, not importance.</p>
<p>A skill is invoked. Something decides that this bounded task is now the task, the skill runs, and it finishes. It has inputs, outputs, and a definition of what a correct result looks like. You can point at a skill and ask whether it did its job.</p>
<p>A system prompt is resident. Nothing invokes it. It is simply there, on the turn where it matters and on the forty turns where it does not.</p>
<p>That gives a clean rule:</p>
<ul>
<li>if the instruction should apply to <strong>everything in this session</strong>, it belongs in the system prompt</li>
<li>if it applies to <strong>one repeated task</strong>, it belongs in a skill</li>
</ul>
<p>Most arguments about this are not really about definitions. They are about a specific rule someone has written and cannot decide where to put. Run it through the test above and the answer is usually immediate.</p>

</table>
<h3 id="what-belongs-in-a-system-prompt">What belongs in a system prompt</h3>
<p>Things that are true regardless of the request:</p>
<ul>
<li>who the model is acting as, and on whose behalf</li>
<li>what it must refuse, and what it must escalate rather than decide</li>
<li>output conventions that apply to everything: format, units, citation style</li>
<li>tone, when tone is a product decision and not a preference</li>
</ul>
<p>The common thread is that none of these change based on what is being asked. They are the conditions, not the work.</p>
<h3 id="what-does-not-belong-in-a-system-prompt">What does not belong in a system prompt</h3>
<p>Task logic. Steps. Anything shaped like <em>when the user asks for X, do Y</em>.</p>
<p>Three costs follow, and only the first is obvious.</p>
<p><strong>It applies when it is irrelevant.</strong> A rule about how to format a migration plan is loaded on the turn where someone asks a definitional question. The model has to hold it and decide it does not apply, on every turn, forever.</p>
<p><strong>It competes for context with the work.</strong> Resident text is not free. Every token of task logic in the system prompt is a token unavailable to the thing the session is actually for, and it is spent on every turn rather than once.</p>
<p><strong>It becomes invisible to review.</strong> This is the expensive one. Code gets diffed. Skills, if you have defined them properly, have inputs and outputs and can be tested. A system prompt is a wall of prose in a settings field, and almost no team has a process that examines it. Rules go in. Nothing takes them out. Nobody reads the whole thing.</p>
<h2 id="act-iii-what-it-costs-when-the-line-moves">Act III: What it costs when the line moves</h2>
<h3 id="the-failure-mode-nobody-catches">The failure mode nobody catches</h3>
<p>Two rules in a long system prompt can contradict each other and never produce a visible error.</p>
<p>The model does not raise an exception when its instructions disagree. It picks one, plausibly and quietly, and keeps going. Output stays fluent. Nothing looks broken. The only symptom is that behaviour is subtly inconsistent in a way that gets blamed on the model being non-deterministic.</p>
<p>It usually is not the model. It is two sentences, written eight weeks apart by two people, sitting four hundred words from each other in a file neither of them has read since.</p>
<p>Naming those rules as skills does not make the model smarter. It makes the contradiction <em>visible</em>, because a skill has a boundary and two skills that disagree can be seen to disagree. That is the entire argument for the split, and it is a governance argument rather than a performance one.</p>
<h3 id="what-this-changes-in-practice">What this changes in practice</h3>
<p>Read your system prompt. Not skim, read. For each line, ask whether it should apply on every turn of every session.</p>
<p>Whatever survives that question is configuration, and it is in the right place. Whatever fails it is a task instruction that has been hiding in the settings, applying when it should not, costing context on every turn, and quietly waiting to disagree with the line someone adds next month.</p>
