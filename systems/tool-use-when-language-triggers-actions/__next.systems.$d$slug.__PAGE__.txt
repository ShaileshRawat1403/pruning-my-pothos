10e:T5cf,<p>A model can describe sending an email in perfect detail and nothing will happen. The description is text. Something else has to read it and act.</p>
<p>That gap is small, easy to talk past, and it is where responsibility for every real effect in a tool-using system lives.</p>
<h2 id="what-actually-happens">What actually happens</h2>
<p>You give the model a list of operations it may ask for, each with a name, a description and expected arguments. Something like <code>get_weather(location)</code> or <code>refund_order(order_id, amount)</code>.</p>
<p>When the model judges one relevant, it does not execute anything. It emits a structured request:</p>
<pre><code class="language-json">{&quot;tool&quot;: &quot;refund_order&quot;, &quot;arguments&quot;: {&quot;order_id&quot;: &quot;A-3391&quot;, &quot;amount&quot;: 40}}
</code></pre>
<p>Your application receives that. It reads the name, checks the arguments, decides whether to proceed, and if it does, calls your own function. Whatever comes back can be handed to the model so it can carry on.</p>
<p><strong>A model does not call a tool. It produces a request, and software decides whether that request becomes an action.</strong></p>
<p>The shorthand &quot;the model called the tool&quot; is convenient and it hides the step that matters. If your implementation routes a structured request through application code, which is the usual arrangement, say so, because the difference shows up the moment something goes wrong.</p>

<h2 id="why-the-distinction-is-load-bearing">Why the distinction is load-bearing</h2>
<p><strong>The code that reads the request is where responsibility for the effect sits.</strong></p>
<p>A request for a refund of forty pounds is a sentence until your code runs it. If the amount was wrong, the model produced a bad proposal and your application made the payment. Both facts matter, and only the second one moved money.</p>
<p>This changes what you build. You are not trying to make the model incapable of asking for the wrong thing; it will sometimes ask for the wrong thing, in the same way it sometimes writes a wrong sentence. You are deciding what your code does when it receives a request it should not honour.</p>
<p>Concretely, the receiving code has work to do before anything runs:</p>
<ul>
<li><strong>Is this a tool I actually expose?</strong> A name in the response is not proof the operation exists.</li>
<li><strong>Do the arguments hold up?</strong> Types, ranges, referenced identifiers. This is <a href="/systems/structured-output-and-why-it-matters/">structured output</a> territory, and it applies here directly.</li>
<li><strong>Should this run at all, now, for this user?</strong> Permission is a separate question from whether the request is well-formed, and it has its own page.</li>
<li><strong>What happens when the tool fails?</strong> Timeouts, errors and partial results are ordinary, and the system needs an answer for each.</li>
</ul>
