<p><strong>Key takeaways</strong></p>
<ul>
<li>Tool use turns language into actions, not just answers.</li>
<li>The app is the gatekeeper for safety and validation.</li>

<p>Tool use gives a Large Language Model the ability to interact with the outside world. It transforms the model from a passive text generator into an active agent that can query databases, call APIs, and perform actions. This capability is powerful, but it introduces significant new risks and responsibilities.</p>
<h3 id="what-changes-when-a-model-can-use-tools">What changes when a model can use tools?</h3>
<p>The moment a model can use tools, language stops being only output and starts becoming a request for execution. This page is for builders designing agentic or automated workflows, and the main shift is that application policy, validation, and auditability matter more than prompt cleverness.</p>
<p>In practice, <span class="highlight">clarity at boundaries reduces downstream errors</span> more than late-stage tuning.</p>
<aside class="callout callout-insight">
  <p><strong>Design note.</strong> Read this page as a tradeoff map: make boundaries explicit, track feedback loops, and optimize only after constraints are clear.</p>
</aside>

<h2 id="act-i-the-fundamentals">Act I: The fundamentals</h2>
<h3 id="the-tool-use-loop">The tool-use loop</h3>
<p>By itself, an LLM can only process text. It cannot access real-time information, interact with other software, or affect the physical world. Tool use, also known as function calling, bridges this gap.</p>
<p>The process begins by providing the LLM with a list of available &quot;tools.&quot; Each tool is a function in your application&#39;s code, described in natural language (e.g., <code>get_current_weather(location: string)</code>). When a user issues a prompt, the model can decide that it needs to use one of these tools. Instead of generating a text response, it generates a structured JSON object specifying the tool to call and the arguments to use.</p>

  <figcaption>The tool-use cycle: the LLM requests an action, the application executes it, and the result informs the final response.</figcaption>
</figure>
<h2 id="act-ii-the-modern-paradigm">Act II: The modern paradigm</h2>
<h3 id="application-as-gatekeeper">Application as gatekeeper</h3>
<p>The application code acts as an intermediary. It inspects the JSON object from the LLM and, if it deems the call safe and valid, executes the requested function. For example, if the LLM generates <code>{ &quot;tool&quot;: &quot;get_current_weather&quot;, &quot;arguments&quot;: { &quot;location&quot;: &quot;Boston, MA&quot; } }</code>, the application would call its internal weather function for Boston.</p>
<p>The result of that function call (e.g., <code>{ &quot;temperature&quot;: &quot;72F&quot;, &quot;conditions&quot;: &quot;Sunny&quot; }</code>) is then passed back to the LLM as part of a new prompt. The LLM, now equipped with this real-time information, generates the final, human-readable response: &quot;The current weather in Boston is 72°F and sunny.&quot; This entire loop can happen in a single turn of conversation.</p>
<h2 id="act-iii-principles-in-practice">Act III: Principles in practice</h2>
<h3 id="guardrails-and-accountability">Guardrails and accountability</h3>
<p>The moment an LLM can trigger an action, the stakes become much higher. A bug is no longer just a poorly worded sentence; it could be an accidental purchase, a deleted file, or an incorrect database query. This elevates the importance of safety and accountability.</p>
<ul>
<li><strong>Never trust the LLM&#39;s output directly.</strong> Always validate the tool name and arguments against a strict schema before execution.</li>
<li><strong>Implement guardrails.</strong> Use confirmation steps for any destructive or costly actions. A prompt like &quot;Are you sure you want to delete this file?&quot; is a critical safety mechanism.</li>
<li><strong>Provide precise tool descriptions.</strong> The LLM&#39;s decision to use a tool is based entirely on the description you provide. Vague or ambiguous descriptions will lead to incorrect tool usage.</li>
<li><strong>Plan for failure.</strong> The tool might fail, an API could be down, or the result might be an error. Your system must be able to handle these failures gracefully and report them back to the LLM.</li>
</ul>
<p>For related systems context, see <a href="/systems/systems-001-foundations/">Systems 001: Foundations</a> and <a href="/systems/from-prompt-to-production/">From Prompt to Production</a>. For an execution-focused companion, use the <a href="/shelf/shared-resources/engineering-agentic-systems-deck/">Engineering Agentic Systems deck</a>. For a review artifact that turns guardrails into a repeatable checklist, use the <a href="/portfolio/">Prompt Safety Checklist</a>.</p>
<p>The shift is quieter than it sounds. You are no longer tuning sentences; you are designing a boundary where a suggestion becomes an effect, and deciding, deliberately, which effects the system is allowed to have. That boundary, not the model, is where trust in a tool-using system actually lives, and it is the part worth most of your attention.</p>
<h3 id="what-this-changes-in-practice">What this changes in practice</h3>
<p>When you give a model tools, you must shift your focus from prompt quality to a system of validation, error handling, and safety guardrails.</p>
