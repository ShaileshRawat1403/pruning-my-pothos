5f:T1741,<p>Ask an assistant something it told you yesterday and it may have no idea what you mean. Ask again in the same conversation and it answers immediately. People reach for the word memory to explain the difference, and that word causes most of the confusion here.</p>
<h2 id="what-it-actually-is">What it actually is</h2>
<p><strong>A context window is the bounded information available to the model for the current run.</strong></p>
<p>Everything the model works from occupies that space: the system instruction, the conversation so far, any documents the application retrieved, the current question, and the response being generated as it grows. It is measured in tokens rather than words or characters, which is why <a href="/systems/a-simple-tokenizer/">token counts</a> and not page counts decide whether something fits.</p>
<p>The important property is the one people skip. The window describes a single run. When the run finishes, nothing in it carries forward on its own.</p>
<h2 id="what-it-is-not">What it is not</h2>
<p>It is not memory.</p>
<p><strong>Persistent memory is a separate application-level mechanism that may store information outside the run and later place selected information into that context.</strong> When an assistant remembers your name next week, an application wrote it down somewhere and put it back into the input before the model was called. The model did not retain it. The parameters are unchanged, which is a different page: <a href="/systems/training-vs-inference/">training, fine-tuning and inference</a>.</p>
<p>This matters practically, not just terminologically. Because that memory lives in ordinary storage, you can inspect it, correct it and delete it. If the model had genuinely absorbed the information, none of those would be available to you.</p>
<p>The phrase &quot;working memory&quot; is a reasonable analogy for the feeling of it, and this page used to lead with it. The analogy misleads on the point that matters most, which is persistence, so it is better to describe the mechanism directly and skip the metaphor.</p>
<h2 id="what-happens-at-the-limit">What happens at the limit</h2>
<p>The old version of this page said the oldest tokens are pushed out of memory. That describes what some applications choose to do, not something the model does.</p>
<p>What actually happens when input exceeds the limit depends on who is handling it:</p>
<ul>
<li><strong>The model or provider</strong> rejects the request, or truncates it according to its own rule.</li>
<li><strong>The application</strong> decides in advance what to leave out, drop, summarise or shorten.</li>
<li><strong>A chat interface</strong> may silently drop or compress older turns on your behalf.</li>
</ul>
<p>Three different systems, three different behaviours, and only the middle one is under your control. If your system needs specific behaviour at the boundary, the honest answer is that you have to implement it rather than assume it.</p>
<h2 id="why-a-bigger-window-is-not-the-whole-answer">Why a bigger window is not the whole answer</h2>
<p>Windows have grown enormously, which invites the conclusion that selection stopped mattering. It did not, for two reasons.</p>
<p>The first is cost and speed. Longer input generally means more to process, so it tends to cost more and take longer. How much more depends on the model and the provider, and the only reliable figures are the ones you measure on your own workload.</p>
<p>The second is that filling a window is not the same as using it well. <strong>Selection and placement can matter as much as raw context size.</strong> You will see one version of this discussed under the name &quot;lost in the middle&quot;. This page has not measured it, so treat the general shape as worth testing rather than as a rule: if your task depends on the model attending to one specific instruction inside a long input, verify that it does, on your own task, rather than assuming position is neutral.</p>
<p>What survives from all this is unglamorous. A short, relevant input is easier to get right than a long one, and it is cheaper.</p>
<h2 id="a-way-to-divide-the-space">A way to divide the space</h2>
<p>This is a PMP working heuristic rather than a standard, and it is useful mainly when a system&#39;s inputs have grown messy. Think of the window as holding three kinds of thing:</p>
<ul>
<li><strong>Persistent core.</strong> Identity, policy, definitions, the constraints that apply to every run.</li>
<li><strong>Task frame.</strong> The current objective and what counts as done.</li>
<li><strong>Evidence pack.</strong> Only the material this particular step needs.</li>
</ul>
<p>The value is not the three names. It is that the categories have different lifetimes, so labelling them makes it obvious which parts should be identical on every call and which should be rebuilt each time. If your inputs are already tidy, you do not need this.</p>
<h2 id="finding-versus-choosing">Finding versus choosing</h2>
<p>One distinction is worth carrying between pages.</p>
<p>Retrieval finds candidate material. Context assembly decides what the model actually receives. A search can surface the right passage and the assembly step can still leave it out, usually because something had to go to fit the budget.</p>
<p>If you are working on what gets found, that belongs to <a href="/systems/retrieval-augmented-generation-in-plain-terms/">retrieval</a>. If you are working on what gets included, you are working on the context window, and this is the page for it.</p>
<h2 id="what-this-changes">What this changes</h2>
<p>Stop treating the window as a store of what the system knows. It is the space for one run, and what goes into it is chosen, by you or by something you did not configure.</p>
<p>Log the assembled input, not just the retrieved candidates. The difference between those two lists is where a surprising number of &quot;it forgot&quot; reports actually come from.</p>
