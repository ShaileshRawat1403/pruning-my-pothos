2f:T1b85,<p>A prompt works. You save it. Next month someone else uses it, gets a different shape of answer, and adjusts the wording. Now there are two versions and no way to say which is right.</p>
<p>What was saved was a phrase. What was needed was everything that was implicit when it worked the first time.</p>
<h2 id="what-a-skill-means-here">What a skill means here</h2>
<p><strong>In PMP, a skill is a reusable, versioned package of instructions and declared operating constraints for a repeated task.</strong> It may define inputs, outputs, tool scope, success criteria, failure conditions and escalation.</p>
<p>Other platforms use the word differently, sometimes for a tool, sometimes for a plugin, sometimes for a saved prompt with a name. This is working vocabulary for describing one architecture, not a claim about what the word means generally.</p>
<p>The load-bearing part is <em>declared</em>. A prompt that happens to be reused is still a prompt. What makes it a skill in this sense is that the things which were assumed are now written down.</p>
<h2 id="what-to-declare">What to declare</h2>
<p>These are design dimensions rather than required fields. A small skill may need three of them; a consequential one probably needs all six.</p>
<p><strong>Purpose.</strong> One sentence naming the job this owns that nothing else should. If it takes a paragraph, you may be describing a workflow.</p>
<p><strong>Inputs.</strong> What must be supplied, what is optional, and what should be ignored. &quot;Ignored&quot; earns its place: skills degrade when callers pass extra context that quietly changes behaviour.</p>
<p><strong>Output shape.</strong> What comes back. If anything downstream depends on it, that shape is a contract, and the mechanics of checking it are <a href="/systems/structured-output-and-why-it-matters/">structured output</a>.</p>
<p><strong>Tool scope.</strong> What it may touch. A skill drafting a release summary does not need billing access. Narrower is easier to validate and easier to reason about later.</p>
<p><strong>Success criteria.</strong> What a correct result looks like, specifically enough that someone else could judge it.</p>
<p><strong>Stop conditions.</strong> What it does instead of guessing: missing input, conflicting evidence, a request beyond its scope. A skill that never stops is either trivial or overconfident.</p>
<h2 id="a-worked-example-and-its-limits">A worked example, and its limits</h2>
<p><strong>This repository packages its own editorial skill as a SKILL.md alongside five recipe files and a validator that checks structure rather than judgment.</strong> The skill file states the contract for publishing here; the recipes carry per-form language rules; the validator runs over both.</p>
<p>The interesting part is the line the skill draws itself. Its own wording is that automation verifies the contract while the author remains accountable for the claim. The validator can confirm that an incident is declared as observed, that a claim maps to prose, and that a repository source carries an immutable commit reference. It cannot confirm that the observation happened, or that a cited source supports the interpretation drawn from it.</p>
<p>That is a useful thing to copy and a precise thing not to overstate. It shows one way to package and check a skill. <strong>It does not establish a universal skill format</strong>, and the validator passing does not mean the writing is any good. It means the declared structure holds.</p>
<h2 id="one-skill-or-two">One skill or two</h2>
<p>The most common design question is whether to split.</p>
<p><strong>If two parts of a skill would be evaluated differently, they probably should not be one skill.</strong> That test does more work than it looks like, because it catches the cases where a single package has quietly acquired two jobs with different definitions of success.</p>
<p>Split it when the parts serve different objectives, carry different risk, produce outputs consumed by different things, or need different tool permissions.</p>
<p>Keep it whole when the steps are tightly coupled to one objective, share the same inputs, share the same definition of done, and stop for the same reasons.</p>
<h2 id="changing-it-without-breaking-it">Changing it without breaking it</h2>
<p>Reuse is what makes a skill valuable and also what makes changing it consequential. A prompt used once has a local blast radius. A skill used in four places does not.</p>
<p>A small set of cases, kept stable, is enough to notice most drift:</p>
<table>
<thead>
<tr>
<th align="left">Case</th>
<th align="left">Question it answers</th>
</tr>
</thead>
<tbody><tr>
<td align="left"><strong>Normal</strong></td>
<td align="left">Does it still do the job on ordinary input?</td>
</tr>
<tr>
<td align="left"><strong>Borderline</strong></td>
<td align="left">Does it stay sensible when the input is thin or ambiguous?</td>
</tr>
<tr>
<td align="left"><strong>Failure</strong></td>
<td align="left">Does it fail clearly when it cannot proceed?</td>
</tr>
<tr>
<td align="left"><strong>Escalation</strong></td>
<td align="left">Does it stop when it should, rather than continuing?</td>
</tr>
</tbody></table>
<p>Four cases you actually run beat forty you intend to write. The point is not coverage; it is that a behaviour change becomes visible instead of arriving as a complaint weeks later.</p>
<p>Signals worth watching after a change: output no longer matches its declared shape, escalation happens less often with no drop in risk, callers start correcting results by hand, or the skill needs more context than it used to.</p>
<p>This is scoped to one question: does this revised package still do what it claims? How to evaluate AI output more generally, and what to record over time, belongs to <a href="/systems/evaluation-is-a-human-problem/">evaluation</a> and <a href="/systems/observability-first-ai-systems/">observability</a>.</p>
<h2 id="versioning">Versioning</h2>
<p>Version when behaviour changes, not when wording does.</p>
<p>A materially changed skill package should remain distinguishable from the version it replaced. Whether a caller has to do anything differently tells you about interface compatibility, not whether the package changed enough to version. A clearer instruction producing the same results is a tidy-up. Changed instructions, a widened tool scope or a weakened stop condition are worth being able to tell apart later, even when nothing downstream has to move.</p>
<p>Whatever scheme you use matters less than being consistent about that line, and recording what changed in behaviour rather than what changed in text. A version number attached to a diff nobody can interpret is bookkeeping.</p>
<h2 id="what-this-changes">What this changes</h2>
<p>Stop asking whether a prompt can be reused. Ask whether the thing you would hand to someone else says what it needs, what it returns, what it may touch, and when it should stop. If it does not say those, reuse will produce a second version rather than a shared one.</p>
