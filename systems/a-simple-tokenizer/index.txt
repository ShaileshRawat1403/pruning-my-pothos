<p><strong>Key takeaways</strong></p>
<ul>
<li><strong>Tokenization</strong> is the process of converting text into numbers (tokens) that a model can process.</li>
<li>Models do not see characters or words; they see a sequence of <span class="highlight">integers</span>.</li>
<li>A &quot;token&quot; is not always a word. It can be part of a word, a space, or a punctuation mark.</li>
<li>This abstraction explains why models struggle with spelling (&quot;Strawberry&quot;) and simple math.</li>
<li>&quot;Shorter&quot; text is not always &quot;simpler&quot; for a model if it uses rare tokens.</li>

<p>Before a Large Language Model (LLM) can &quot;think,&quot; it must read. But computers cannot read text; they can only process numbers. The <strong>Tokenizer</strong> is the bridge component that chops human language into atomic units called tokens and assigns each one a unique integer ID.</p>
<p>This seems like a trivial implementation detail, but it dictates the fundamental capabilities and limitations of the model.</p>
<aside class="callout callout-insight">
  <p><strong>Design note.</strong> Read this page as a tradeoff map: make boundaries explicit, track feedback loops, and optimize only after constraints are clear.</p>
</aside>

<h2 id="act-i-the-fundamentals">Act I: The fundamentals</h2>
<h3 id="why-not-just-characters">Why Not Just Characters?</h3>
<p>We could map <code>a=1</code>, <code>b=2</code>, <code>c=3</code>. This is simple, but inefficient.</p>
<ul>
<li><strong>Context window:</strong> If every letter is a token, the sentence &quot;The quick brown fox&quot; is 19 tokens.</li>
<li><strong>Compute cost:</strong> Attention mechanisms scale quadratically with sequence length. Longer sequences = much slower and more expensive models.</li>
</ul>
<p>Conversely, we could map every <em>word</em> to a number. But English has hundreds of thousands of words, and new ones are invented daily. The vocabulary would be too large to compute efficiently.</p>
<p>The solution is <strong>Subword Tokenization</strong>: break common words into whole tokens (<code>&quot;apple&quot;</code>) and rare words into chunks (<code>&quot;un&quot;</code>, <code>&quot;friend&quot;</code>, <code>&quot;li&quot;</code>, <code>&quot;ness&quot;</code>).</p>
<h3 id="what-a-token-actually-looks-like">What a Token Actually Looks Like</h3>
<p>To a human, the word &quot;Smart&quot; is a single concept. To a tokenizer, it might be one token (ID: <code>5421</code>).</p>
<p>But the word &quot;Smartification&quot; (a made-up word) might be split into three tokens:</p>
<ol>
<li><code>Smart</code> (ID: <code>5421</code>)</li>
<li><code>ifi</code> (ID: <code>892</code>)</li>
<li><code>cation</code> (ID: <code>1102</code>)</li>
</ol>
<p>The model processes these three integers in sequence. It learns that <code>5421</code> followed by <code>892</code> usually implies a transformation of the concept &quot;Smart&quot;.</p>
<p>Here is a <strong>toy tokenizer</strong> you can run locally. It is not BPE, but it shows the idea of splitting text into chunks.</p>
<pre><code class="language-python">import re

text = &quot;Smartification!&quot;
tokens = re.findall(r&quot;[A-Za-z]+|[^A-Za-z\\s]&quot;, text)
print(tokens)
</code></pre>
<h2 id="act-ii-the-modern-paradigm">Act II: The modern paradigm</h2>
<h3 id="the-reality-subword-tokenization">The Reality: Subword Tokenization</h3>
<p>Real systems (like GPT-4 or Claude) use algorithms like <strong>Byte Pair Encoding (BPE)</strong>. BPE starts with characters and iteratively merges the most frequent adjacent pairs until a target vocabulary size is reached.</p>
<p>This explains why LLMs struggle with tasks that seem easy to humans:</p>
<ol>
<li><strong>Spelling:</strong> The model sees the token ID <code>12345</code> for &quot;Strawberry&quot;. It does not inherently see the letters <code>r-r</code>. It has to memorize the spelling as a separate fact.</li>
<li><strong>Math:</strong> The number <code>9.11</code> might be tokenized as <code>[9, ., 11]</code> while <code>9.9</code> is <code>[9, ., 9]</code>. To the model, <code>11</code> is &quot;bigger&quot; than <code>9</code>, so it might hallucinate that 9.11 is greater than 9.9.</li>
</ol>
<h2 id="act-iii-principles-in-practice">Act III: Principles in practice</h2>
<h3 id="why-this-matters-for-systems">Why This Matters for Systems</h3>
<p>When designing systems around LLMs, tokenization creates invisible constraints:</p>
<ul>
<li><strong>Cost:</strong> You pay per token. Verbose prompts cost more.</li>
<li><strong>Performance:</strong> &quot;Prompt Engineering&quot; is often just finding words that tokenize into patterns the model recognizes more strongly.</li>
<li><strong>Security:</strong> Some &quot;jailbreaks&quot; work by forcing the tokenizer to split forbidden words in ways that bypass safety filters (e.g., splitting &quot;bomb&quot; into &quot;b-omb&quot;).</li>
</ul>
<p>Understanding the tokenizer means understanding the raw material of the intelligence you are orchestrating.</p>
<p>For related systems context, see <a href="/systems/systems-001-foundations/">Systems 001: Foundations</a> and <a href="/systems/from-prompt-to-production/">From Prompt to Production</a>. You can find empirical measurements of context usage and degradation in our <a href="/shelf/local-experiments/context-window-stress/">Context window stress test local experiment</a>.</p>
<h3 id="what-this-changes-in-practice">What this changes in practice</h3>
<p>Treat tokenization as a design constraint: it shapes cost, reliability, and the kinds of prompts your system can handle.</p>
