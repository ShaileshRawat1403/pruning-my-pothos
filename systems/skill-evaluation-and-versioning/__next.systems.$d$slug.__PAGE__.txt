<p><strong>Key takeaways</strong></p>
<ul>
<li>Skills need expected behavior definitions before they need version numbers.</li>
<li>Regression detection depends on stable test cases and clear output contracts.</li>
<li>Versioning should track behavior changes, not only text edits.</li>
<li>Rollback decisions should be based on impact and reversibility, not intuition alone.</li>
</ul>
</blockquote>
<p>Once a skill becomes reusable, it creates a new operational problem: how do you change it safely? A prompt can be edited casually because its blast radius is often local. A skill is different. It may sit inside workflows, feed downstream systems, or operate under tool permissions that make changes consequential.</p>
<p>That is why skills need evaluation and versioning. Without them, the same mechanism that makes a skill reusable also makes its failures repeatable at scale.</p>
<h3 id="what-does-it-mean-to-evaluate-a-skill">What does it mean to evaluate a skill?</h3>
<p>Evaluating a skill means checking whether it still performs its intended task under the expected inputs, constraints, and escalation rules. The evaluation should confirm not only output quality, but also whether the skill behaved within its contract.</p>
<p>In practice, <span class="highlight">a skill version is only meaningful when the expected behavior is explicit</span>.</p>
<aside class="callout callout-insight">
  <p><strong>Design note.</strong> If a team cannot describe what changed in the behavior of a skill, versioning becomes record-keeping theater instead of an operational safeguard.</p>
</aside>

<h2 id="act-i-define-what-should-stay-stable">Act I: Define what should stay stable</h2>
<h3 id="expected-behavior-before-version-numbers">Expected behavior before version numbers</h3>
<p>Do not start with the version label. Start with the behavior that must remain understandable.</p>
<p>A skill should define:</p>
<ul>
<li>what task it is supposed to accomplish</li>
<li>what output shape it promises</li>
<li>what constraints it should respect</li>
<li>what circumstances require escalation</li>
<li>what side effects are allowed or forbidden</li>
</ul>
<p>If these stay implicit, a version number does not help much. You can say the skill moved from <code>v1.2</code> to <code>v1.3</code>, but that does not explain whether the skill became safer, more permissive, more accurate, or more fragile.</p>
<p>This is why <a href="/systems/designing-reusable-ai-skills/">Designing Reusable AI Skills</a> comes first. Design establishes the contract. Evaluation and versioning protect that contract over time.</p>
<h3 id="what-should-be-tested">What should be tested</h3>
<p>The most useful test set usually includes:</p>
<ul>
<li>one normal case</li>
<li>one borderline case</li>
<li>one failure or missing-input case</li>
<li>one escalation-required case</li>
</ul>

<p>These do not need to become an overly large suite. They need to stay stable enough that behavior changes can be noticed early.</p>
<h2 id="act-ii-detect-and-manage-change">Act II: Detect and manage change</h2>
<h3 id="regression-detection">Regression detection</h3>
<p>Regression detection is less about perfection than about noticing the wrong kind of drift.</p>
<p>Useful regression signals include:</p>
<ul>
<li>output no longer matches the contract</li>
<li>escalation happens less often when risk is unchanged</li>
<li>the skill requires more context than before</li>
<li>downstream workflows need extra correction</li>
<li>a safer old behavior is replaced by a more confident but less bounded one</li>
</ul>
<p>This is the same logic used in <a href="/systems/evaluation-as-a-runtime-discipline/">Evaluation as a Runtime Discipline</a>. The skill should not only be judged on what it says, but on whether it still behaves correctly as part of a runtime system.</p>
<h3 id="versioning-logic">Versioning logic</h3>
<p>Versioning is useful when it reflects behavior, not only edits.</p>
<p>A practical rule:</p>
<ul>
<li><strong>patch-level change</strong>: wording or structure improved without changing behavior expectations</li>
<li><strong>minor change</strong>: behavior expanded or tightened without changing the core purpose</li>
<li><strong>major change</strong>: output contract, tool authority, or escalation logic changed in a way that affects downstream use</li>
</ul>
<p>The exact labels matter less than consistency. People using the skill should be able to tell whether the change is cosmetic, operational, or breaking.</p>
<p>If you want a compact starting structure, use the <a href="/shelf/shared-resources/ai-skill-design-templates/">AI skill design templates</a> page and treat the review template as the minimum change log.</p>
<h3 id="change-communication">Change communication</h3>
<p>Versioning fails when no one knows what changed.</p>
<p>Good change communication includes:</p>
<ul>
<li>short summary of what changed</li>
<li>expected behavior difference</li>
<li>affected workflows or downstream dependencies</li>
<li>test cases used for verification</li>
<li>any rollback caveats</li>
</ul>
<p>This is where skill design starts to look more like software operations than prompt curation. That is a good sign.</p>
<h2 id="act-iii-decide-whether-to-keep-or-roll-back">Act III: Decide whether to keep or roll back</h2>
<h3 id="rollback-conditions">Rollback conditions</h3>
<p>Rollback should not feel dramatic. It should be a normal response to the wrong kind of change.</p>
<p>Rollback is usually appropriate when:</p>
<ul>
<li>the skill violates its output contract</li>
<li>tool or side-effect boundaries become less safe</li>
<li>key test cases fail</li>
<li>downstream workflows degrade noticeably</li>
<li>escalation behavior weakens under uncertainty</li>
</ul>
<p>Rollback is especially important when the skill is reused in several places. The cost of one bad change compounds quickly when reuse is the whole point.</p>
<h3 id="failure-patterns-to-watch">Failure patterns to watch</h3>
<p>Several patterns often indicate that a skill needs rollback or redesign:</p>
<ul>
<li>success rate appears stable but manual correction rises</li>
<li>a version improves one case by weakening boundary behavior elsewhere</li>
<li>the skill becomes more verbose instead of more reliable</li>
<li>the team cannot explain why the new version should be trusted more</li>
<li>&quot;small&quot; edits repeatedly change how downstream systems must interpret the output</li>
</ul>
<p>These are operational warnings, not editorial preferences.</p>
<p>For the conceptual layer, see <a href="/systems/what-a-skill-is-in-ai-systems/">What a Skill Is in AI Systems</a>. For the comparison layer, see <a href="/systems/skills-vs-prompts-vs-agents/">Skills vs Prompts vs Agents</a>.</p>
<h3 id="what-this-changes-in-practice">What this changes in practice</h3>
<p>You stop treating skill updates as casual prompt edits and start treating them as controlled behavior changes that need tests, versions, and rollback logic.</p>
