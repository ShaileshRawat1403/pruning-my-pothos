<p>This article is for builders and operators who want AI-assisted website maintenance without giving an agent the authority to publish directly. It is a small case study in using an agentic workflow to prepare a website post without letting the workflow publish on its own.</p>
<p>The site goal was simple: draft a public article for pruningmypothos.com titled &quot;AI website publishing with human-in-the-loop control.&quot; The larger goal was more important: show that an agent can help maintain a live website while staying inside an explicit governance boundary.</p>
<p>The distinction is simple:</p>
<p><strong>Flowright prepares and governs; humans approve and publish.</strong></p>
<p>The agentic system can prepare the work, record evidence, and make the review packet easier to inspect. It does not own the final authority.</p>

<h2 id="act-i-the-baseline-problem">Act I: The baseline problem</h2>
<h3 id="why-does-agentic-publishing-need-a-boundary">Why does agentic publishing need a boundary?</h3>
<p>A website is not only a place where words appear. It is a public interface for judgment, positioning, search visibility, reputation, and trust. That makes &quot;let the agent publish it&quot; a poor default.</p>
<p>The risk is not that an agent drafts bad prose. Bad prose is easy to edit. The larger risk is that the system blurs the line between preparation and authority.</p>
<table class="data-table">
  <thead>
    <tr>
      <th>Stage</th>
      <th>Autonomous Publishing</th>
      <th>Human-in-the-Loop Gate</th>
    </tr>
  </thead>
  <tbody>
    <tr>
      <td><strong>Content Intake</strong></td>
      <td>Raw prompt / automated scrape</td>
      <td>Declared goal, constraints, source docs</td>
    </tr>
    <tr>
      <td><strong>Draft Generation</strong></td>
      <td>Unchecked direct output</td>
      <td>Validated against style and topic rubric</td>
    </tr>
    <tr>
      <td><strong>Pre-flight Checks</strong></td>
      <td>Skipped or basic build check</td>
      <td>Schema, link integrity, asset verification</td>
    </tr>
    <tr>
      <td><strong>Promotion / Deploy</strong></td>
      <td>Agent pushes directly to prod</td>
      <td>Workflow halts; human signs off handoff</td>
    </tr>
  </tbody>
</table>
<p>A useful assistant can summarize site intent, turn source material into a draft, check for obvious structure gaps, and prepare an export packet. But the authority to publish belongs somewhere else.</p>
<p>This matters more when the website is part of a broader operating system. A post about governed AI work should not be produced by an ungoverned publishing path. The method needs to match the message.</p>
<aside class="callout">
  <p><strong>Design note.</strong> The workflow's value isn't in what it can produce. It's in the fact that it stops. A workflow that can draft, verify, and package but cannot publish is more useful for real operations than one that publishes fast and asks forgiveness later.</p>
</aside>
<h3 id="the-baseline-problem">The baseline problem</h3>
<p>The baseline state was ordinary website maintenance: a human could ask an AI tool for a draft, copy material into the site, run a build, and publish.</p>
<p>That can work for a single post, but it leaves weak evidence. The missing record usually looks like this:</p>
<ul>
<li>what the workflow was asked to do;</li>
<li>what source material it used;</li>
<li>what constraints it followed;</li>
<li>where it paused;</li>
<li>who approved the handoff;</li>
<li>whether publication was automatic or manual.</li>
</ul>
<p>For this proof, those questions became the work. The goal was not only to write an article. The goal was to test whether the article could move through a governed loop.</p>
<h2 id="act-ii-the-websiteops-loop">Act II: The WebsiteOps loop</h2>
<h3 id="the-websiteops-loop">The WebsiteOps loop</h3>
<p>The WebsiteOps workflow followed this shape:</p>
<pre><code class="language-text">intake website state
-&gt; audit existing pages
-&gt; plan content update
-&gt; draft new content
-&gt; verify links and SEO
-&gt; human review
-&gt; export publish packet
-&gt; capture performance feedback
</code></pre>
<p>The loop is intentionally modest. It does not claim to solve content strategy. It does not claim to understand every nuance of the live site.</p>
<p>It creates a repeatable path for a specific kind of work: prepare a public website update from declared inputs, verify the draft against basic constraints, pause for review, and export a packet only after approval.</p>
<p>That is enough to change the operating model. Instead of treating website updates as loose prompting, the update becomes a governed run with declared inputs and a visible stop condition.</p>
<h3 id="what-was-governed">What was governed</h3>
<p>The workflow can produce artifacts, but it cannot decide that those artifacts should go live. It can record evidence, but it cannot use that evidence as a substitute for human approval. It can export a packet, but the export is still a handoff, not publication.</p>
<table>
<thead>
<tr>
<th>Stage</th>
<th>Agentic work</th>
<th>Governance boundary</th>
</tr>
</thead>
<tbody><tr>
<td>Intake</td>
<td>Accept the site goal, target section, source material, SEO requirements, and publish constraints.</td>
<td>The workflow starts from declared inputs rather than an open-ended prompt.</td>
</tr>
<tr>
<td>Draft</td>
<td>Prepare a public case-study draft and publish packet.</td>
<td>The draft is an artifact, not a live site change.</td>
</tr>
<tr>
<td>Verification</td>
<td>Check readiness constraints before review.</td>
<td>Passing validation does not grant publication authority.</td>
</tr>
<tr>
<td>Review</td>
<td>Pause at the human review gate.</td>
<td>A human must approve before export or implementation handoff.</td>
</tr>
<tr>
<td>Promotion</td>
<td>Remain blocked from autonomous promotion.</td>
<td>Publication stays a separate human-controlled commit, deploy, or CMS action.</td>
</tr>
</tbody></table>
<p>This is the useful part of the proof. The system does not become safer by saying &quot;human-in-the-loop&quot; in the abstract. It becomes safer when the workflow has a specific place where it must stop.</p>
<h2 id="act-iii-validation-and-what-changed">Act III: Validation and what changed</h2>
<h3 id="validation">Validation</h3>
<p>The WebsiteOps run was created from a declared site goal and explicit publishing constraints. It produced a draft artifact, passed the workflow&#39;s validation step, and stopped at <code>human_review</code>.</p>
<p>That pause is the behavior the system is supposed to show.</p>
<p>Because the test environment could not reach the model gateway, the run used Flowright&#39;s deterministic fallback generator. That is a limitation of draft quality, not a failure of the governance test. The governance behavior still held: the workflow created artifacts, recorded evidence, validated, and stopped before export.</p>
<p>The human review then becomes a real editorial checkpoint, not a decorative approval button. The reviewer can reject the packet, request revision, or approve it for export. Even after approval, Flowright does not publish the article to pruningmypothos.com. It only prepares the handoff.</p>
<h3 id="before-and-after">Before and after</h3>
<p>Before the loop, the website update could have been a normal AI-assisted writing task.</p>
<p>After the loop, the update has a clearer operating shape:</p>
<ul>
<li>the intent is declared;</li>
<li>the draft is artifacted;</li>
<li>validation happens before review;</li>
<li>human approval is required;</li>
<li>export is a handoff;</li>
<li>promotion remains denied.</li>
</ul>
<p>That last point matters. Promotion denial is not a defect in this workflow. It is the proof that WebsiteOps is not an autonomous publishing tool. The denial preserves the difference between &quot;prepare this for me&quot; and &quot;ship this for me.&quot;</p>
<h3 id="what-this-changes-in-practice">What this changes in practice</h3>
<p>For a personal site, this is enough to create a repeatable WebsiteOps loop:</p>
<ol>
<li>Open a site goal.</li>
<li>Attach source material and constraints.</li>
<li>Generate a draft packet.</li>
<li>Verify structure and links.</li>
<li>Review as the human owner.</li>
<li>Apply the approved change manually.</li>
<li>Build, inspect, and publish.</li>
</ol>
<p>The workflow does not remove judgment. It makes judgment easier to place.</p>
