f7:T5f3,<p>A model&#39;s parameters are fixed once training ends, so anything private, recent or specific to your situation has to arrive some other way. Retrieval is that other way: fetch material when the request comes in, and put it into the input. The idea is simple. The failures are not, because they happen at several different points and look identical from the outside.</p>
<h2 id="the-stages">The stages</h2>
<p>Between a question and a grounded answer there are usually six stages.</p>
<p><strong>Source material.</strong> Documents, records, pages, tickets. Whatever holds the answer.</p>
<p><strong>Preparation and indexing.</strong> The material is cleaned, often split into smaller passages, and stored so it can be searched. If a document never made it in, nothing downstream can find it.</p>
<p><strong>Retrieval.</strong> A search returns candidates for this question. Usually more than you will use.</p>
<p><strong>Ranking and filtering.</strong> The candidates are ordered, and most are dropped.</p>
<p><strong>Context assembly.</strong> What survives is placed into the input alongside the instruction, the conversation so far, and anything else the application adds.</p>
<p><strong>Generation.</strong> The model produces an answer from what it was handed.</p>
<p>Not every system has all six as separate components.</p>
<p>Small ones collapse several into one search call. But the stages are worth separating in your head, because when the answer is wrong, exactly one of them usually lost the evidence.</p>

<h2 id="what-search-means-here">What &quot;search&quot; means here</h2>
<p>RAG is often described as though it means a vector database. It does not. Vector search is one retrieval mechanism among several, and the choice between them is a real design decision.</p>
<p><strong>Lexical retrieval</strong> matches the words themselves. Ask for an error code, a part number or a surname, and matching the literal string is exactly what you want. This is mature technology and it does not stop being useful because embeddings exist.</p>
<p><strong>Vector retrieval</strong> compares embeddings, which are numeric representations positioned so that related text lands near related text. This is what lets a query about &quot;small dog&quot; reach a passage that only says &quot;puppy&quot;.</p>
<p><strong>Hybrid retrieval</strong> runs both and combines the results, which is common precisely because the two fail in different places.</p>
<p><strong>Reranking</strong> is a second pass over the candidates the first pass returned, usually with a slower and more accurate model, to reorder them before anything is kept.</p>
<p>Lexical search misses a paraphrase. Vector search misses an exact identifier, and will happily return something topically adjacent instead of admitting it found nothing. Neither weakness is a bug; they are properties of what each method compares.</p>

<p>Treat the embedding model as a replaceable component rather than a fixed source of truth. Different models arrange the space differently, so the right one is the one whose near neighbours match your material, measured on your own queries rather than on a public leaderboard.</p>
<h2 id="the-honest-boundary">The honest boundary</h2>
<p><strong>Retrieval can provide evidence to the model. It does not guarantee that the evidence is relevant, sufficient, current or correct, nor that the model will use it correctly.</strong></p>
<p>You will read that retrieval fixes hallucination. It does not. It changes where the problem lives. A model given a wrong document will now be wrong with a citation attached, which is harder to catch, not easier.</p>
<h2 id="where-it-actually-fails">Where it actually fails</h2>
<p>When a grounded answer comes back wrong, walk the stages in order:</p>
<ul>
<li>the material was never indexed</li>
<li>it was indexed but the search did not return it</li>
<li>it was returned but ranked below the cut</li>
<li>it survived ranking but was dropped during assembly, for length or another reason</li>
<li>it reached the model and the model did not use it</li>
</ul>
<p>Only the last of those is a model problem. The rest are retrieval and assembly problems, and they are fixable with ordinary engineering. This page owns one question: was the needed evidence indexed, retrieved, ranked and selected? Whether the final answer was any good is a separate question, and it is answered by <a href="/systems/evaluation-is-a-human-problem/">evaluation</a> rather than here.</p>

<h2 id="keeping-the-material-worth-retrieving">Keeping the material worth retrieving</h2>
<p>Retrieval quality has an upstream dependency that is easy to neglect, because it looks like documentation work rather than engineering.</p>
<p>Content tends to grow faster than structure. As a store fills with near-duplicates and drifting names, searches start returning something related instead of the right thing, and the outputs stay fluent while getting quietly worse. A small store with clear ownership and scope usually beats a large one without.</p>
<p>Two habits carry most of the weight. Give each unit an owner and a scope, so somebody can answer whether a page is still true. And check freshness deliberately, because a store that was correct when it was built will not stay correct on its own.</p>
<p>One stage sits even further upstream. If the text was corrupted on the way in, no amount of retrieval quality recovers it. That is the subject of <a href="/systems/why-ocr-quietly-breaks-document-ai/">why OCR quietly breaks document AI</a>.</p>
<h2 id="what-this-changes">What this changes</h2>
<p>Before adding a bigger model or a cleverer prompt, find out whether the evidence reached the input at all. Log what was retrieved and what was actually assembled, because those are different lists and the gap between them is where a surprising number of failures live.</p>
<p>For how the assembled material competes for limited space, see <a href="/systems/context-windows-as-working-memory/">context windows</a>.</p>
