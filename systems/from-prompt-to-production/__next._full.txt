<p>It is easy to get an LLM to do something cool once. It is hard to get it to do something useful 10,000 times in a row without embarrassing the company.</p>
<p>This checklist is designed for <strong>non-technical leaders</strong> and <strong>product owners</strong> who are deploying AI workflows. It forces you to slow down and think about the system, not just the magic.</p>
<h3 id="what-changes-when-a-prompt-becomes-production-software">What changes when a prompt becomes production software?</h3>
<p>The moment a prompt becomes production software, it stops being a clever instruction and becomes a managed operating contract. This guide is for product teams and leaders turning prototypes into repeatable workflows, and the real shift is from isolated prompting to defined interfaces, evaluation, monitoring, and fallback.</p>

<h2 id="act-i-the-fundamentals">Act I: The fundamentals</h2>
<h3 id="define-intent-the-contract">Define Intent (The Contract)</h3>
<p>Before writing a prompt, write a sentence describing exactly what the AI should do—and what it should <strong>not</strong> do.</p>
<ul>
<li><strong>Goal:</strong> &quot;Summarize customer support tickets.&quot;</li>
<li><strong>Constraint:</strong> &quot;Do not invent details. If the ticket is unclear, state &#39;Unclear&#39;.&quot;</li>
<li><strong>Persona:</strong> &quot;Act as a senior support agent.&quot;</li>
</ul>
<h3 id="identify-risks-the-red-team">Identify Risks (The Red Team)</h3>
<p>What is the worst thing that could happen? Be specific.</p>
<ul>
<li><strong>Hallucination:</strong> Inventing a refund policy that doesn&#39;t exist.</li>
<li><strong>Toxicity:</strong> Responding rudely to an angry customer.</li>
<li><strong>Data Leak:</strong> Revealing one customer&#39;s data to another.</li>
</ul>
<aside class="callout">
  <p><strong>Action:</strong> Create a "Red Team" document where you try to break your own prompt. Feed it confusing, angry, or malicious inputs and see what happens.</p>
</aside>
<h2 id="act-ii-the-modern-paradigm">Act II: The modern paradigm</h2>
<h3 id="set-inputsoutputs-the-interface">Set Inputs/Outputs (The Interface)</h3>
<p>Natural language is fluid, but your business systems are not. Define the structure.</p>
<ul>
<li><strong>Input:</strong> &quot;Raw text from email body, truncated to 2000 tokens.&quot;</li>
<li><strong>Output:</strong> &quot;JSON object containing <code>{ summary, sentiment, urgency_score }</code>.&quot;</li>
</ul>
<p>Forcing the model to output structured data (JSON) is the single best way to make it reliable for software integration.</p>
<p>Here is a simple <strong>prompt contract</strong> you can copy into your docs or configs:</p>
<pre><code class="language-yaml">intent: summarize_support_ticket
inputs:
  - id: ticket_body
    type: string
outputs:
  - id: summary
    type: string
  - id: sentiment
    type: string
constraints:
  max_words: 120
  pii: disallow
</code></pre>
<h3 id="validate-the-eval">Validate (The Eval)</h3>
<p>Do not deploy until you have run your prompt against at least 50 examples.</p>
<ul>
<li><strong>Gold Set:</strong> 50 real examples from history.</li>
<li><strong>Metric:</strong> How many did it get right?</li>
<li><strong>Threshold:</strong> &quot;We will not deploy until accuracy &gt; 90%.&quot;</li>
</ul>
<h2 id="act-iii-principles-in-practice">Act III: Principles in practice</h2>
<h3 id="monitor-drift-the-pulse">Monitor Drift (The Pulse)</h3>
<p>Once deployed, the system will degrade. Not because the code rots, but because the world changes.</p>
<ul>
<li><strong>Log everything:</strong> Save every input and output.</li>
<li><strong>Spot checks:</strong> Have a human review 1% of daily traffic.</li>
<li><strong>User feedback:</strong> Add a &quot;thumbs down&quot; button. If a user clicks it, that data point goes straight to the engineering team.</li>
</ul>
<h3 id="human-fallback-the-safety-net">Human Fallback (The Safety Net)</h3>
<p>Probabilistic systems <strong>will</strong> fail. You need a plan for when (not if) that happens.</p>
<figure class="diagram">
  <iframe src="/scenes/human-fallback-flow.html" title="Human Fallback Flow" loading="lazy" scrolling="no" style="pointer-events: none;"></iframe>
  <figcaption>The "Human in the Loop" is not a bug; it's a feature of high-reliability systems.</figcaption>
</figure>
<p>If the AI&#39;s confidence score is low, or if a guardrail is triggered, the system should <strong>fail gracefully</strong> to a human. Do not show the user a hallucination. Show them a message: <em>&quot;I&#39;m not sure about that, let me connect you to a specialist.&quot;</em></p>

<p>Ship fewer demos and more reliable systems: lock intent, validate early, and plan for human fallback before launch.</p>
