2:T12ad,<p>Use these when a prompt you keep pasting has started doing a job. A prompt is the input to one run; a skill is the same job written down once, with what it takes, what it returns, and what counts as done. The difference is explained in <a href="/systems/skills-vs-prompts-vs-agents/">skills vs prompts vs agents</a>.</p>
<p>There are three templates. Most skills only ever need the first.</p>
<h2 id="1-skill-definition-template">1. Skill definition template</h2>
<p>Fill this in when a task repeats and you want the same result from it every time.</p>
<pre><code class="language-yaml">name:
objective:
inputs:
constraints:
tools:
output_format:
success_criteria:
failure_modes:
escalation:
</code></pre>
<p>What each field is for:</p>
<ul>
<li><strong>name</strong>: what people will call it. One job, one name.</li>
<li><strong>objective</strong>: the single outcome, in one sentence. If it needs &quot;and&quot;, it may be two skills.</li>
<li><strong>inputs</strong>: what it is given, and in what shape. Anything not listed here is not its responsibility.</li>
<li><strong>constraints</strong>: what it must not do or change. The easiest field to leave empty and the one reviews end up being about.</li>
<li><strong>tools</strong>: which tools it may call. None is a valid answer.</li>
<li><strong>output_format</strong>: the shape of what comes back, precise enough for code to check.</li>
<li><strong>success_criteria</strong>: how you would know it worked, written so two people would agree.</li>
<li><strong>failure_modes</strong>: the ways it is known to go wrong, so they can be checked for.</li>
<li><strong>escalation</strong>: what happens when it cannot finish: stop, retry, or hand to a person.</li>
</ul>
<p>An illustrative example, filled in:</p>
<pre><code class="language-yaml">name: extract-invoice-fields
objective: Return the invoice number, total and currency from one invoice.
inputs: The text of a single invoice.
constraints:
  - Do not guess a field that is not on the invoice.
  - Do not convert currencies.
tools: none
output_format: JSON with invoice_id (string), total (number), currency (ISO code)
success_criteria: All three fields match the invoice, or are null when absent.
failure_modes:
  - Several totals on one invoice (subtotal, tax, total).
  - Currency shown only as a symbol.
escalation: If more than one total could be the answer, return null and flag it.
</code></pre>
<h2 id="2-skill-review-template">2. Skill review template</h2>
<p>Fill this in when a skill changes, so the change in behaviour is written down rather than discovered.</p>
<pre><code class="language-yaml">skill_version:
change_summary:
expected_behavior_change:
test_cases:
rollback_note:
</code></pre>
<ul>
<li><strong>skill_version</strong>: the version this change produces. Bump it when behaviour changes, not when wording does.</li>
<li><strong>change_summary</strong>: what was edited.</li>
<li><strong>expected_behavior_change</strong>: what should now come out differently. &quot;None&quot; is a claim worth testing.</li>
<li><strong>test_cases</strong>: the inputs that show the change, including at least one that should not have changed.</li>
<li><strong>rollback_note</strong>: how to go back if it misbehaves.</li>
</ul>
<h2 id="3-skill-composition-template">3. Skill composition template</h2>
<p>Fill this in when one skill&#39;s output becomes another step&#39;s input.</p>
<pre><code class="language-yaml">trigger:
upstream_context:
skill_execution:
output_contract:
downstream_handoff:
</code></pre>
<ul>
<li><strong>trigger</strong>: what starts this skill.</li>
<li><strong>upstream_context</strong>: what it receives from the step before.</li>
<li><strong>skill_execution</strong>: which skill runs, and at which version.</li>
<li><strong>output_contract</strong>: what the next step can rely on, usually the definition&#39;s output_format.</li>
<li><strong>downstream_handoff</strong>: who or what receives it, and what happens if the output fails its check.</li>
</ul>
<h2 id="where-these-stop">Where these stop</h2>
<p>A template is a contract on paper. It makes a disagreement cheap, because it shows up in a field before it shows up in a result. It does not enforce anything: a constraint written here is still an instruction until something checks it. Deciding where a skill&#39;s boundary sits, and when one skill should be two, is covered in <a href="/systems/designing-reusable-ai-skills/">designing reusable AI skills</a>.</p>
