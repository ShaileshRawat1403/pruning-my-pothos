The experience was useful because it forced me to see the platform the way Azure sees it: as a system of locks, not a single machine. <h2 id="architecture-map">Architecture map</h2>
<p>Azure makes more sense when you separate where things live from who can touch them.</p>
<ul>
<li><strong>Subscription</strong> is the billing boundary.</li>
<li><strong>Resource group</strong> is your organizational box.</li>
<li><strong>Services</strong> are the active components: AI Foundry, Postgres, the app host.</li>
<li><strong>Identity</strong> decides who can act.</li>
<li><strong>Networking</strong> decides where traffic can flow.</li>
</ul>

<h2 id="what-happened">What happened</h2>
<p>I had a Spring Boot backend, a PostgreSQL database with <code>pgvector</code>, and a hosted LLM. The first deployment looked clean, but the system behaved like it was unplugged. The database connection timed out, and the LLM endpoint returned 404s even with the correct API key.</p>
<p>The fix was not in the code. It was in the cloud posture.</p>
<h2 id="the-two-gates">The two gates</h2>
<p>Identity is the first gate. In Azure AI Foundry, the deployment name is part of the contract. If the app expects <code>gpt-4o</code> and the deployment is named something else, the request fails without a helpful error.</p>
<p>Networking is the second gate. PostgreSQL Flexible Server starts in a default-deny posture. I had to explicitly open the Azure Firewall for my IP and allow internal Azure services.</p>

<h2 id="portal-walkthrough">Portal walkthrough</h2>
<p>This is the most compact first-time path I found. The goal is to prove the system works before you optimize it. Treat this as a tour of Azure&#39;s main control surfaces.</p>
<ol>
<li><strong>Create a resource group.</strong> This is your container for everything that follows.</li>
<li><strong>Create PostgreSQL Flexible Server.</strong> Choose a basic tier. Turn on the <code>pgvector</code> extension after the instance is running.</li>
<li><strong>Open the firewall.</strong> Add your current IP and allow Azure services. Without this, connections will fail even if credentials are correct.</li>
<li><strong>Create an Azure AI Foundry project.</strong> Deploy a model and give it a deployment name you will use in code.</li>
<li><strong>Collect the endpoint + key.</strong> Treat these as the root of your API contract.</li>
</ol>

<h2 id="first-time-config">First-time config</h2>
<p>I kept the first run intentionally small. One model. One database. One backend. Azure gets easier when the first pass is narrow.</p>
<p>Wire the app with explicit environment variables. Avoid hidden defaults for the first pass.</p>
<pre><code class="language-bash">export AZURE_OPENAI_ENDPOINT=&quot;https://&lt;resource-name&gt;.openai.azure.com&quot;
export AZURE_OPENAI_API_KEY=&quot;&lt;your-key&gt;&quot;
export AZURE_OPENAI_DEPLOYMENT=&quot;&lt;deployment-name&gt;&quot;
export DATABASE_URL=&quot;postgresql://&lt;user&gt;:&lt;password&gt;@&lt;db-hostname&gt;:5432/&lt;db-name&gt;&quot;
</code></pre>

<h2 id="quick-checks">Quick checks</h2>
<p>Check the database port is reachable:</p>
<pre><code class="language-bash">nc -vz &lt;db-hostname&gt; 5432
</code></pre>
<p>Confirm the database allows your connection:</p>
<pre><code class="language-bash">psql &quot;postgresql://&lt;user&gt;:&lt;password&gt;@&lt;db-hostname&gt;:5432/&lt;db-name&gt;&quot;
</code></pre>
<p>Verify the model deployment is reachable (Azure OpenAI-style endpoints):</p>
<pre><code class="language-bash">curl -s \
  -H &quot;api-key: $AZURE_OPENAI_API_KEY&quot; \
  -H &quot;Content-Type: application/json&quot; \
  &quot;$AZURE_OPENAI_ENDPOINT/openai/deployments/$AZURE_OPENAI_DEPLOYMENT/chat/completions?api-version=2024-06-01&quot; \
  -d &#39;{&quot;messages&quot;:[{&quot;role&quot;:&quot;user&quot;,&quot;content&quot;:&quot;ping&quot;}],&quot;max_tokens&quot;:5}&#39;
</code></pre>
<h2 id="failure-modes">Failure modes</h2>
<ul>
<li>The deployment name in code does not match the Azure AI Foundry deployment name.</li>
<li>The database firewall blocks your IP, even if credentials are correct.</li>
<li>The endpoint URL is right but the API version is not supported.</li>
<li>Secrets are scattered across files and the app reads the wrong one.</li>
</ul>
<h2 id="what-made-the-difference">What made the difference</h2>
<p>I mirrored the deployment name in my app config so there was no drift between code and Azure AI Foundry. I treated firewall setup as a prerequisite, not a later fix. And I validated the model endpoint with <code>curl</code> before touching Spring Boot.</p>
<h2 id="what-i-would-do-next-time">What I would do next time</h2>
<p>I would open networking first, even before spinning up the app. I would validate the model endpoint and database with CLI probes to keep feedback tight. And I would centralize deployment names and resource groups from day one, because config drift hides the real problem.</p>
